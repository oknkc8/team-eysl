## 3. 마이그레이션 번호 대장

**번호를 직접 고르지 마십시오.** 공유 dev DB에서 두 번 충돌했고, 그때마다 파일 이름과
`schema_migrations` 행이 어긋나는 창이 생겼습니다. **중복 번호는 오늘 아무 데서도 오류를
내지 않습니다** — `schema_migrations`가 번호가 아니라 전체 파일명으로 키를 잡기 때문에
`0036_a.sql`과 `0036_b.sql`이 평범한 두 행으로 앉습니다.

```
0044  record_uploads 경로 검증                            적용됨
0045  race_entry                                          적용됨
0046_a 회수된 객체는 쓸리지 않는다                          적용됨
0047  chat_attachments                                    적용됨
0048  훈련 상세          머지됨 · 적용됨
0049_a 채팅 첨부 이름     PR #53 · 적용됨
0050  활동 댓글 + 푸시    머지됨 · 적용됨
0051  계정 없는 출석      PR #70 머지됨 · 적용됨 · **0052 가 되돌림**
0052  0051 되돌리기       PR #74 · 적용됨
0053  다음               비어 있음
```

**이미 적용된 마이그레이션을 고쳤다면 `migrate.sh` 는 건너뜁니다.** 대장에 행이 있으면
`skip` 이고, 그 파일은 다시 실행되지 않습니다. `0051` 을 리뷰 지적대로 고칠 때 실제로 겪었고,
DDL 은 그대로이고 `create or replace` 와 `grant` 만 바뀐 경우라 **함수 구간만 잘라 따로
적용**했습니다. 파일 전체를 다시 돌리면 `add column` 과 `drop constraint` 가 터집니다.

앞으로 같은 상황이면 셋 중 하나이고, **어느 쪽인지는 「무엇이 바뀌었나」가 정합니다.**

**A. 함수 본문만 바뀐 경우 — 그 구간만 적용합니다.** `create or replace` 와 `grant` 는 몇 번
실행해도 같으므로 안전합니다. 파일 전체를 다시 돌리면 `add column`·`drop constraint` 가 터집니다.

```bash
# 파일에서 첫 create or replace 이후만 잘라 낸다
python3 -c "s=open('app/supabase/migrations/00NN_x.sql').read(); \
  i=s.find('create or replace function'); open('/tmp/fns.sql','w').write(s[i:])"
bash app/scripts/psql.sh -v ON_ERROR_STOP=1 --single-transaction -f /tmp/fns.sql
```

`--single-transaction` 이 중요합니다. 중간에 실패하면 절반만 적용된 상태로 남지 않습니다.

**B. DDL 이 바뀐 경우 — 새 번호로 후속 마이그레이션을 씁니다.** 이미 적용된 파일을 고치는 것이
아니라, 차이를 메우는 마이그레이션을 하나 더 쓰는 것입니다. 다른 사람이 이미 원래 것을 적용한
DB 가 있을 수 있으므로 이쪽이 유일하게 안전합니다.

**C. 대장 행 삭제 — 조건이 맞을 때만입니다.** 잘못 쓰면 **이미 적용된 DDL 을 다시 실행**하게
되고, 공유 dev DB 에서는 남의 작업 위에서 그렇게 됩니다.

```sql
-- 1. 정확한 version 을 확인한다. migrate.sh 는 번호가 아니라 전체 파일명으로 skip 한다
select version from public.schema_migrations where version like '00NN%';
-- 2. 그 마이그레이션의 DDL 이 실제로 적용돼 있는지 본다 (컬럼·제약·인덱스를 직접 확인)
select column_name from information_schema.columns
 where table_schema='public' and table_name='<table>';
```

**2번이 「적용돼 있다」로 나오면 C 는 쓸 수 없습니다.** 행만 지우고 다시 돌리면 그 DDL 이
두 번째로 실행되어 실패하거나, 더 나쁘게는 성공하면서 다른 것을 덮습니다. C 는 **DDL 이 아직
적용되지 않았는데 대장 행만 남은 경우** — 즉 A 나 손수 실행이 어긋나게 만든 상태 — 에만
해당합니다.

그리고 어느 경우든 먼저 **지금 누가 이 DB 를 쓰고 있는지** 확인하십시오. 공유입니다.

**`psql -f`로 마이그레이션을 돌리면 대장에 남지 않습니다. 반드시 `migrate.sh`를 쓰십시오.**

`0048`이 한때 이 목록에서 빠져 있었고, 원인이 그것이었습니다. `bash scripts/psql.sh -f
<migration>`은 SQL만 실행합니다. `schema_migrations`에 행을 쓰는 것은 `migrate.sh`이고,
그것도 `--single-transaction`으로 마이그레이션과 대장 행을 함께 커밋합니다.

**그때 검증이 전부 통과한 이유가 여기 있습니다.** 「함수가 있나」와 「병합이 되나」를 물었고
둘 다 참이었습니다. **「대장이 아나」는 묻지 않았습니다.** 객체의 존재와 대장의 기록은 서로
다른 사실인데, 앞의 것으로 뒤의 것을 확인했다고 여긴 것입니다. 이 저장소가 반복해서 밟는
형태 — 검사가 실제로 물은 질문과, 답했다고 생각한 질문이 다른 것.

**적용 순서는 번호 순서가 아닙니다.** 공유 DB라 각자 자기 브랜치 것을 적용하고, 그래서
가운데가 빕니다. 「최고 번호가 N이니 N까지 다 돌았다」는 추론은 여기서 성립하지 않습니다 —
목록을 보고 빠진 것을 찾으십시오.

**번호를 받기 전에 볼 곳 셋.** 로컬 `ls`는 답이 아닙니다 — 한 워크트리는 다른 워크트리의
미푸시 파일을 볼 수 없습니다.

1. `public.schema_migrations` — 이미 적용된 것 전부. dev DB가 공유라 모든 브랜치의 작업이
   여기 모입니다.
2. **모든 원격 브랜치**의 `app/supabase/migrations/`. **`git fetch`를 먼저** 하지 않으면
   피하려던 그 낡은 목록을 다시 읽습니다.
3. `git worktree list` 후 각 디렉터리 — 5분 전에 옆 워크트리에서 쓰이고 아직 푸시 안 된
   파일은 위 둘 **어디에도** 없습니다.

**uuid는 첫 그룹 꼬리에 넣습니다.** 마지막 그룹은 시드 더미의 인덱스를 담고 있어

한 번은 27개 signup·댓글 E2E로, 한 번은 전체 E2E로 다시 실행해 잡았다.

**로그인 없는 회원 fixture가 있다.** 명단 추가 테스트는 그 전용 회원을 전용 활동에
추가 → `명단에 있음` 확인 → 다시 빼기까지 한다. 실제 회원을 첫 행으로 고르는 테스트는 금지다.

signup이 만든 계정은 **닉네임·이메일 패턴으로 지우지 않는다.** 성공한 signup은 별도 브라우저로
로그인해 자기 Auth ID와 member ID를 `app/e2e/.auth/owned-signups/`에 기록한다. seed와 teardown은

테스트 데이터가 남을 수 있지만, 실제 회원을 지우는 대신 **안전하게 실패**한 것이므로 ID를 확인해

이 항목이 오래 재현되지 않은 이유가 여기 있습니다. **시작점이 깨끗하지 않으면 끝점의 숫자가

「누수인가」가 아니라 **「지금 누가 돌고 있나」**입니다 — `/proc`으로 보십시오, `ps`는 이
환경에서 못 셉니다.

네임스페이스가 없다는 것이 정체를 말해 줍니다 — **시드 픽스처가 아니라 `signup.spec.ts`가 실제
가입 흐름으로 만든 계정**입니다. 그리고 ledger가 비어 있으므로 **아무 정리도 그들을 이름 댈 수
없습니다.** `cleanup.sql`은 더 이상 닉네임·이메일 패턴으로 지우지 않고, ledger가 유일한
손잡이입니다.

원인은 이 파일이 이미 예상해 둔 그것입니다 — 프로세스가 signup 직후 ledger 기록 전에 죽는 것.
오늘 여러 세션이 사용량 한도로 그렇게 끝났습니다.

**처방대로 exact-ID 수동 정리를 했습니다.** ID 22개를 먼저 파일로 캡처하고, 트랜잭션 안에서
지우되 **실제 회원 수가 41이 아니면 `raise`로 전체를 되돌리도록** 걸었습니다. 목록이 틀렸다면
커밋 자체가 일어나지 않는 형태입니다. 결과는 회원 22 · identity 22 · auth 22 삭제, 가드 통과,
이후 `members=41 no_login=36 with_login=5 attendance=234 records=258 activities=35 pwtest=0`으로
기준선 복귀.

**여기서 알아야 할 것은 구조적 귀결입니다.** ledger는 「정리가 **실제 회원**을 지울 수 있다」를
「정리가 **테스트 회원**을 놓칠 수 있다」로 바꾼 것입니다. 그 거래는 옳습니다 — 두 실패의 값이
비교가 안 됩니다. 다만 **놓친 쪽은 조용히 쌓이고, 이 데이터베이스에는 실제 명단이 같이
있습니다.** 오늘은 3명이 `approved`라 명단 화면에 실제 회원처럼 서 있었습니다.

그래서 **세는 것이 이 설계의 필수 짝입니다.** 러너가 없을 때 이 값은 0이어야 합니다.

```sql
select count(*) from public.members where nickname like 'pwtest%';
```

**0이 아니면 그 자체가 결함이 아니라 「어떤 실행이 끝을 못 봤다」는 신호**이고, 위와 같은
exact-ID 정리로 처리합니다. 패턴으로 지우는 로직을 되살리는 것은 이 거래를 거꾸로 되돌리는
것이라 하지 않습니다.

## 7. 다른 머신에서 시작하기

**먼저 읽으십시오 — clone만으로는 되지 않습니다.** 저장소에 **일부러 넣지 않은** 것 셋이
있고, 그것들은 사람이 옮겨야 합니다. 셋 다 없으면 앱이 뜨지 않거나, 뜨더라도 빈 데이터베이스를
봅니다.

| 저장소에 없는 것 | 어디서 오는가 | 없으면 |
|---|---|---|
| `.env`와 `app/.env`의 **값** | Supabase 대시보드 | `vitest`가 첫 단언 전에 죽고 `psql`이 안 붙음 |
| **클럽 워크북 `.xlsx`** | 방장님, 또는 본인 사본 | 스키마는 서지만 회원·기록·출석이 0 |
| **dev Supabase 프로젝트** | 만든 사람의 계정 | 아래 |

**세 번째가 가장 조용하고 가장 비쌉니다.** dev 프로젝트가 특정 계정에 묶여 있고 그 계정을
잃으면, 데이터베이스가 통째로 사라집니다. 스키마는 마이그레이션으로 되살아납니다 —
`npm run db:migrate`가 50개를 처음부터 다시 놓습니다. **되살아나지 않는 것은 데이터입니다.**
회원 41명·기록 258건·출석 234행은 전부 워크북에서 임포트한 것이고, **임포터는 저장소에 있지만
워크북은 없습니다**(`app/scripts/import-club-workbook.sh`, `app/scripts/import/`).

그러니 프로젝트를 새로 만들어야 한다면 순서가 이렇습니다.

```bash
# 1. 새 Supabase 프로젝트를 만들고 .env 두 개를 채운다 (.env.example 이 형태를 다 적어둠)
cd app && npm ci
npm run db:migrate                       # 스키마 50개
bash scripts/import-club-workbook.sh <워크북 경로>   # 데이터
npx playwright install chromium          # 브라우저는 npm ci 로 안 옴
```

**워크북을 저장소에 넣지 마십시오.** 실명·연락처가 든 실제 회원 명부이고 이 저장소는
공개입니다. 임포터만 저장소에 있고 재료는 밖에 있는 지금 구조가 의도된 것입니다.

**VAPID 개인 키도 마찬가지로 저장소 밖입니다.** `.env.example` 아래쪽에 어디에 무엇을 넣는지
적혀 있습니다 — 공개 키만 `app/.env`, 개인 키는 `supabase secrets set`으로 프로젝트에.
**둘은 반드시 같은 `generate-vapid-keys` 실행에서 나와야 합니다.** 짝이 안 맞으면 모든 화면이
정상으로 보이고 모든 구독이 저장되며 모든 알림이 401로 거절되는데, 회원은 그걸 볼 수 없습니다.

**옮겨온 뒤 제대로 됐는지는 이렇게 확인합니다** — 게이트가 아니라 데이터부터 보십시오.

```sql
select count(*) from public.members;      -- 41 (그중 36명이 로그인 없음)
select count(*) from public.records;      -- 258
select count(*) from public.attendance;   -- 234
```

수가 다르면 임포트가 덜 된 것이고, 게이트는 그 상태에서도 초록입니다.

**새 체크아웃에서 세 가지가 필요합니다.** 하나라도 빠지면 게이트가 이상하게 실패합니다.

```bash
cd app && npm ci          # node_modules 는 따라오지 않습니다
npx playwright install chromium   # 브라우저도 npm ci 로 안 옵니다
```

**`psql`도 따라오지 않고, 설치해도 PATH에 안 잡힙니다.** 2026-09-02에 새 머신에서
확인했습니다. `brew install libpq`가 맞는 패키지인데(전체 postgres 서버가 아니라 클라이언트만),
libpq는 **keg-only**라 `/opt/homebrew`에 심볼릭 링크가 걸리지 않습니다. 그래서 설치 직후에도
새 셸에서는 `psql: command not found`이고, `npm run db:migrate`가 마이그레이션 문제처럼 보이는
얼굴로 죽습니다.

```bash
brew install libpq
echo 'export PATH="'"$(brew --prefix libpq)"'/bin:$PATH"' >> ~/.zshrc
exec zsh          # 지금 셸에도 반영
```

**경로를 손으로 적지 말고 `brew --prefix libpq`에 물으십시오.** Apple Silicon은
`/opt/homebrew`, Intel Mac은 `/usr/local`이고, Homebrew prefix를 옮겨 쓰는 사람도 있습니다.
하드코딩하면 다른 머신에서 조용히 틀립니다 — 이 파일의 목적이 바로 그 「다른 머신」입니다.

**이것이 「빠진 도구가 다른 문제로 위장하는」 계열의 예입니다.** 실패 메시지는 `migrate.sh`
안에서 나오므로 마이그레이션이나 접속 설정을 먼저 의심하게 되는데, 실제 원인은 PATH입니다.
`command -v psql`을 **새 로그인 셸에서** 물어보는 것이 판별법입니다 — 지금 셸에서 export를
해두었다면 그 셸에서는 계속 참이라 아무것도 알려주지 않습니다.

**`db:types`는 Docker 데몬을 요구하고, 실패하면 `database.ts`를 파괴합니다.**

이쪽이 더 위험합니다. `gen-types.sh`는 **생성이 성공했는지 알기 전에 대상 파일로
리다이렉트**하므로, Docker 가 없다는 오류 한 줄에 `app/src/types/database.ts`가
**1802줄에서 1줄로 잘렸습니다**(2026-09-02 실측). 그 파일은 손으로 유지하는 예외를 담고
있으므로, 잃으면 생성기가 되돌려 주지 않는 것까지 함께 잃습니다.

```bash
# 백업 -> 실행 -> 망가졌으면 복원. 세 줄을 한 세트로 쓰십시오.
cp app/src/types/database.ts /tmp/database.ts.bak
cd app && npm run db:types
# 실패했거나 파일이 짧아졌으면:
cp /tmp/database.ts.bak app/src/types/database.ts
```

**복원이 필요한지 판단하는 법은 줄 수입니다.** 정상이면 1800줄 언저리이고, 실패하면 1줄이
됩니다. `wc -l app/src/types/database.ts` 로 즉시 압니다. `/tmp` 는 재부팅에 사라지므로,
바로 되돌리지 않을 거면 백업을 다른 곳에 두십시오.

**Docker 가 없으면 대안은 손으로 넣는 것**이고, 그 파일은 이미 그렇게 유지되는 예외를 둘 갖고
있으므로 새로 만드는 관례가 아닙니다. 절차는 이렇습니다.

1. 라이브 DB 에 실제 모양을 묻습니다. **마이그레이션 문면이 아니라 카탈로그입니다.**

```sql
-- 테이블: 컬럼과 nullable 여부
select column_name, data_type, is_nullable from information_schema.columns
 where table_schema='public' and table_name='<table>' order by ordinal_position;
-- 함수: 인자와 반환 타입
select pg_get_function_arguments(oid), pg_get_function_result(oid)
  from pg_proc where proname='<fn>' and pronamespace='public'::regnamespace;
```

2. `Tables.<t>` 의 `Row`/`Insert`/`Update` 세 곳과 `Functions.<fn>` 을 **함께** 고칩니다.
   `0051` 때 `Functions` 만 고치고 `Tables.attendance` 를 빠뜨렸고, 그다음 라운드에서
   `Functions.attendance_for_activity_v1` 의 반환 타입을 또 빠뜨렸습니다. 한 번에 하나씩
   고치면 매번 하나가 남습니다.

3. 고친 뒤 **타입체크만으로는 확인되지 않는다는 것**을 기억하십시오. `getRoster` 처럼 결과를
   캐스트하는 호출부가 있으면 틀린 타입도 조용히 통과합니다. 캐스트하는 곳을 먼저 찾아
   그쪽 기대값과 대조하는 편이 빠릅니다.

**`.env`가 둘입니다** — 둘 다 git-ignored라 새 체크아웃에 없습니다.

- 루트 `.env` — `psql` 스크립트용
- **`app/.env`** — vite·vitest용. **이게 없으면 `vitest`가 첫 단언 전에 죽습니다**
  (`src/lib/env.ts`의 zod 검증이 모듈 로드 시점에 던집니다). **psql이 된다고 vitest가 되는
  게 아닙니다.** 어떤 테스트가 걸리는지는 파일 이름으로 찾지 말고 조건을 만들어 보십시오:
  `mv app/.env app/.env.off && npx vitest run; mv app/.env.off app/.env`

**`router.test.ts` 가 전체 실행에서 한 번 깨졌고 재현되지 않았습니다 (2026-09-02).**

같은 커밋·같은 명령으로 전체를 돌렸을 때 한 번은 `1 failed | 39 passed`, 그다음은
`40 passed`. 그 파일만 단독으로 돌리면 55개가 전부 통과합니다. 그러니 그 파일 자체의 결함이
아니라 **전체 실행에서만 나타나는 상호작용**이고, 아직 원인을 모릅니다.

**한 번 초록을 초록으로 읽지 마십시오.** 이 항목이 남아 있는 이유가 그것입니다 — 재현되지
않았다는 것은 없다는 뜻이 아니라 **아직 못 잡았다**는 뜻이고, 다음에 같은 것을 보면 그때가
두 번째입니다. 보이면 실패한 실행의 출력을 통째로 여기 붙여 주십시오. 순서 의존인지
공유 상태인지는 두 사례를 나란히 놓아야 갈립니다.

**게이트는 다섯입니다. 하나가 초록이라고 나머지가 초록이 아닙니다.**

```bash
cd app
./node_modules/.bin/tsc --noEmit                    # src
./node_modules/.bin/tsc -p tsconfig.functions.json  # supabase/functions
./node_modules/.bin/tsc -p tsconfig.e2e.json        # e2e
./node_modules/.bin/tsc -p tsconfig.scripts.json    # scripts
./node_modules/.bin/vitest run
npm run test:e2e
npm run shots      # 스크린샷 전용, 기본 실행에서 빠져 있습니다
```

**`npx tsc`를 쓰지 마십시오** — 래퍼가 출력을 「TypeScript compilation completed」로 갈아
치우고 실제 오류를 삼킵니다. `./node_modules/.bin/tsc`를 쓰고 종료 코드를 보십시오.

**dev DB는 공유입니다.** 남의 미머지 마이그레이션이 이미 적용돼 있을 수 있으니, 실패를
조사할 때 `schema_migrations`와 자기 브랜치의 파일 목록을 대조하십시오.

**로컬 메모리는 따라오지 않습니다.** `~/.claude/projects/.../memory/`는 이 머신에만
있습니다. 다른 머신에서 이어받는 데 필요한 것은 전부 이 파일과 `CLAUDE.md`에 있어야 합니다.

## 8. 결정된 것 중, 코드만 봐서는 알 수 없는 것

- **첨부 경로를 받는 함수는 서버가 경로를 만들어야 합니다.** 세 모양이 공존합니다 —
  `save_notice_v1`은 서버 유도, `send_message_v1`은 클라이언트가 보내고 검증,
  `record_uploads`는 검증이 없었습니다(`0044`가 닫음). **첫째가 가장 좋습니다. 없는
  파라미터는 틀릴 수가 없습니다.**
- **`activities.details`는 병합해야 합니다**(`||`). 통째 교체가 백필된 출석부를 파괴하는
  방장님 결함의 원인이고, `0048`이 red/green으로 재현했습니다.
- **스토리지 키는 ASCII만.** 한글이 들어가면 Supabase가 `400 InvalidKey`를 냅니다. 읽을 수
  있는 이름은 청구 표의 `file_name` 컬럼에 둡니다 — **키는 식별자, 이름은 데이터.**
  이 결함이 모든 게이트를 통과한 이유는 **버킷에 객체가 0개였기 때문**입니다. 바이트를
  스토리지로 보내 본 테스트가 하나도 없었습니다.
- **e2e 하네스의 락 프로토콜을 손으로 재현하지 마십시오.** 각 조각이 실제 사고 하나씩에
  대응합니다. 줄이면 그 사고가 돌아옵니다 — 이유는 주석에 있습니다.
- **RLS 정책 식은 호출한 롤로 평가됩니다.** `SECURITY DEFINER`는 함수 *본문*의 권한을
  정할 뿐, 호출자의 EXECUTE 필요를 면제하지 않습니다. `0043`이 이걸 놓쳐 앱의 모든 업로드를
  깼고, 마이그레이션은 깨끗하게 적용됐으며 다음 업로드 전까지 아무것도 실패하지 않았습니다.
- **`npm run db:types`는 손으로 고친 것을 조용히 되돌립니다.** `gen-types.sh`는 후처리 없이
  `supabase gen types`의 출력을 파일에 통째로 덮어씁니다. 그래서 **재생성 뒤에는 두 가지를
  되돌려야 합니다.**
  - `member_link_summary_v1` — 어떤 클라이언트 롤에도 EXECUTE가 없어서 일부러 뺍니다.
    타입에 없어야 실수로 호출했을 때 런타임이 아니라 컴파일이 깨집니다.
  - `save_notice_v1`의 `p_notice_id`와 `p_expected_updated_at` — dev에는 `string | null`로
    들어가 있고 생성기는 그렇게 만들지 않습니다. `2ab2153`(#24)에서 손으로 넣은 것입니다.
    생성기는 DEFAULT가 있는 파라미터를 `p_attachment_path?: string`처럼 **옵셔널**로 만들 뿐
    nullable로는 만들지 않습니다. 되돌리지 않으면 `notices/api.ts`의 `?? null` 두 줄이
    깨지고, **그게 마치 `dev`가 레드인 것처럼 보입니다** — 실제로 그렇게 보고된 적이 있습니다.

  **이건 정책이 아니라 두 개의 예외입니다.** 「권한 없는 함수는 다 빼라」로 일반화하지
  마십시오. 세 번째가 생기면 그때 여기에 한 줄 더합니다.
- **정원을 주는 네 경로는 모두 `activities` 행을 먼저 잠급니다.** 2026-08-31에 라이브
  `pg_get_functiondef`로 확인했습니다 — `apply_to_activity` · `activity_enrol_member_v1` ·
  `offer_seat_to_next_waitlister` · `respond_waitlist_offer` 넷 다 `select … from
  public.activities where id = ? for update`가 첫 잠금이고, 그다음에야 `members`나
  `activity_applications`로 갑니다.

  **이 순서가 불변식입니다.** 어느 하나가 `activity_applications`를 먼저 잠그면 나머지 셋과
  잠금 순서가 뒤집혀 교착이 납니다. 그리고 `activities`를 먼저 잡는 덕분에 정원 판정이
  직렬화되어, 스태프 대리 등록과 일반 신청이 같은 자리를 두고 만나도 과예약되지 않습니다 —
  방장님 앱의 「훈련 정원 경합」 결함이 우리 쪽에 없는 이유가 이것입니다.

  **`for update`를 세는 것만으로는 확인되지 않습니다.** 첫 시도에서 정규식이
  `offer_seat_to_next_waitlister`의 주석 한 줄(`FOR UPDATE, unlike 0006…`)을 잠금으로 세어
  순서를 판정하지 못했습니다. 세지 말고 **순서를 읽으십시오.**
- **스크린샷은 문서 재료가 아니라 게이트입니다.** 화면에 적힌 문장은 코드가 아니라서
  **어떤 게이트도 대상으로 삼지 않습니다.** 실제로 두 번, 각자 자기 수정 때문에 화면 문구가
  거짓이 된 것을 스크린샷이 잡았습니다. 타입체크·유닛·diff 리뷰 어느 것도 못 잡습니다.
